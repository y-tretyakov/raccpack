**Источник:** архитектурный разбор (аудио) + текущее состояние `dev` / wiki

**Цель:** зафиксировать три системных улучшения, место их внедрения и критерии приёмки. Каждый блок ниже можно развернуть в отдельную спеку этапа.

## 1. Атомарные откаты и транзакционная оркестрация `raid`

### Проблема

Текущий (планируемый) fail-fast в `raid` при ошибке одной фазы (например, pack после успешного stash) прерывает выполнение со `success: false`, но уже созданные age-архивы и staging-артефакты остаются. Пользователь вынужден вручную убирать «сирот». Это нарушает обещание надёжности.

### Целевое решение

- Весь `raid` выполняется в одном `staging/{raid_id}/`.
- **Write-Ahead Log (WAL)** фиксирует каждый побочный эффект **до** его выполнения.
- Финальные пути в `den/secrets/`, `den/packs/`, `den/manifests/` появляются только через атомарный `rename` при 100 % успехе.
- При любой ошибке: откат по WAL в обратном порядке + удаление staging.
- Режим по умолчанию — **Atomic**. Legacy FailFast — только по флагу `--fail-fast` (отладка).

### Куда в roadmap

**Фаза A3** (Alpha, до 0.3.0). Raid ещё не реализован — внедряем атомарность сразу.

### Этапы (для отдельных спеков)

| ID | Этап | Кратко |
|----|------|--------|
| A3.0 | Orphan-фикстуры | Regression-тесты «частичный успех оставляет артефакты» |
| A3.1 | Единый staging | `staging/{raid_id}/` на весь raid |
| A3.2 | WAL | Append-only журнал Create/Rename/Delete |
| A3.3 | Rollback-движок | Обратный проход WAL + очистка |
| A3.4 | Facade raid | stash → rinse → pack → atomic commit; режимы Atomic/FailFast |
| A3.5–A3.7 | CLI, progress, manifest, E2E | Отчётность + зелёные orphan-тесты |

### Критерии приёмки

- Любой сбой внутри `raid` оставляет den и рабочую копию в исходном состоянии.
- Orphan-тесты зелёные.
- Dry-run не создаёт WAL и не трогает FS.
- Resume **не** входит в эту итерацию (можно добавить позже поверх WAL).

## 2. Композитные детекторы и DAG стека

### Проблема

Модель «один язык = один файл + статическая таблица приоритетов» теряет контекст вложенности. На монорепозитории (Rust backend + React frontend) инструмент может «увидеть» только Rust, удалить `target/` и оставить гигантский `node_modules` — или наоборот.

### Целевое решение

- Сохранить модульность детекторов (один язык/экосистема ≈ один модуль).
- Ввести **WorkspaceDetector / CompositeDetector**:
  - опрашивает все модули реестра;
  - строит **DAG** технологий внутри дерева;
  - сливает экспертные мнения в богатое дерево проекта (не выбирает одного победителя).
- `rinse` и `pack` используют DAG: чистят/упаковывают только релевантные поддеревья.
- Режим `PriorityTable` остаётся default до явного включения `CompositeDag` (обратная совместимость).

### Куда в roadmap

Новая веха **Detect v2 (0.4.x)** — после стабильного Alpha (raid) и до Beta UI. Так TUI/Desktop сразу получат корректное дерево стека.

### Этапы (для отдельных спеков)

| ID | Этап | Кратко |
|----|------|--------|
| D1.1–D1.3 | Реестр + trait + config | `StackDetector`, `detect.mode` |
| D2.1–D2.3 | Composite + конфликты + совместимость | DAG, merge мнений, плоский `stack` + `stack_tree` |
| D3.1–D3.3 | Влияние на rinse/sniff + фикстуры | Релевантная очистка, тесты monorepo |

### Критерии приёмки

- На типичном monorepo `sniff` показывает корректное дерево.
- `rinse` удаляет только релевантный мусор.
- Legacy PriorityTable продолжает работать без изменений поведения.

## 3. Эфемерная верификация секретов (Safe Reveal)

### Проблема

Masked-by-default без безопасного просмотра создаёт слепую зону. Пользователь видит только `***` / хеши и не может отличить false-positive (тестовый токен) от реальной утечки → либо привыкает к шуму, либо случайно удаляет нужный код.

### Целевое решение

- По умолчанию всё masked (инвариант сохраняется).
- Opt-in **ephemeral reveal**:
  - **CLI:** интерактивный флаг/подкоманда, защищённый терминальный ввод, значение стирается из history.
  - **Desktop:** IPC `reveal_secret_ephemeral` → сырая строка напрямую в изолированный React-компонент (минуя Zustand) → zeroize при закрытии модалки.
  - **TUI:** аналогичный безопасный modal.
- Сырое значение никогда не попадает в глобальный store, логи, JSON-отчёты.
- Опциональный audit-log факта запроса (без самого значения).

### Куда в roadmap

**Beta (0.5.x):** B2 (Desktop) + B3 (Security hardening). Нужны UI-поверхности и hardened core.

### Этапы (для отдельных спеков)

| ID | Этап | Кратко |
|----|------|--------|
| B3.4 | Контракт EphemeralSecret | In-memory, Drop + zeroize, не serde |
| B3.5 | CLI interactive reveal | Защищённый ввод, стирание history |
| B2.5 | Desktop reveal | IPC + изолированный компонент |
| B1.5 | TUI reveal | Безопасный modal |
| B3.6–B3.7 | Threat-model + audit | Тесты no-leak, опциональный audit-log |

### Критерии приёмки

- Пользователь может безопасно проверить конкретную находку.
- Сырой секрет не остаётся в состоянии приложения, на диске, в логах или history.
- Reveal выключен по умолчанию и требует явного opt-in.

## Сводка размещения

```text
Alpha 0.3.0     A3  ─── атомарный raid (WAL + rollback)
Detect v2 0.4.x D1–D3 ── композитный DAG
Beta 0.5.0      B2/B3 ── ephemeral reveal + security
```

## Рекомендуемый порядок работ прямо сейчас

1. **A3.0** — orphan-фикстуры и красные regression-тесты (дешёво, даёт защиту).
2. **A3.1–A3.3** — staging + WAL + rollback (ядро атомарности).
3. Дальше по A3 до зелёного E2E raid.
4. После 0.3.0 — Detect v2.
5. В Beta — reveal вместе с UI.

## Что сознательно отложено

- Resume после сбоя (можно добавить поверх WAL позже).
- Сторонние плагины детекторов.
- Автоматический redact / PR «удали секреты».
- Облачный den / KMS.
