# D4.1 — Дизайн: raid по корню проектов

**Статус:** design / contract  
**Проблема:** сейчас только `racc raid --project <one>`. Чтобы упаковать каждый репо отдельно, пользователь пишет shell-цикл по выводу `sniff` — неудобно и легко ошибиться.

---

## 1. Цель

Одна команда:

```bash
racc raid --root ~/DEV/PROJS --den ~/.raccpack/den
racc raid --root ~/DEV/PROJS --den ~/.raccpack/den --yes
```

1. Находит проекты **так же, как sniff** (тот же discover + detect.mode).
2. Для **каждого** проекта выполняет **отдельный** `raid` (свой `.age`, свой `.tar.zst`, свой manifest).
3. Не смешивает секреты/код разных проектов в один архив.

---

## 2. Контракт (решения)

| Тема | Решение |
|------|---------|
| Обнаружение | Тот же pipeline, что `sniff` (candidates + stack). `detect.mode` из config/CLI. |
| Гранулярность | **1 project = 1 raid** (не один tar на весь root). |
| Порядок | Детерминированный: sort by `path` (как sniff). |
| Ошибка одного | **Continue by default**: остальные проекты идут; итог `success=false`, если хоть один failed. |
| `--fail-fast` (batch) | Опционально: остановить batch после первого failed project (не путать с raid FailFast mode внутри проекта). |
| Dry-run | Default: все проекты только plan, без FS. |
| Passphrase | Один раз на весь Commit-batch (env или один prompt), та же identity на каждый project raid. |
| Den | Общий `--den`; артефакты различаются slug/ts/short_id как сейчас. |
| Parallel | **v1 sequential only** (проще passphrase, den, progress). `parallel_jobs` — follow-up post-0.4. |
| Фильтры | `--only name-or-path-substr` (repeatable); без match → skip. |
| Лимит | `--limit N` для отладки. |
| Взаимоисключение | `--project` **или** `--root`, не оба. |
| Пустой root | Ok + message «0 projects»; exit 0. |

---

## 3. Почему не «один огромный pack на root»

- Секреты разных репо в одном age — плохой blast radius и restore.
- Пользователь явно хочет **отдельные** архивы (формулировка задачи).
- Atomic rollback осмыслен на уровне **одного** project tree.

---

## 4. Связь с Detect v2

- `priority_table` / `composite_dag` влияют на **какие** paths считаются project roots и как заполнен stack — batch просто итерирует список.
- Не требует DAG для MVP batch; выигрыш DAG — точнее boundaries на монорепо (один monorepo = один project path, внутри stack_tree).
