# M2.2 — Detect languages/frameworks → `Stack`

**Фаза:** M2 — Sniff (обнаружение проектов)  
**Веха:** MVP → 0.1.0  
**Статус этапа:** todo  
**Зависимости:** M2.1 (`ProjectCandidate`, markers), M1.2 (`Stack`)  
**Параллельность:** Dev + Test одновременно

---

## 1. Цель этапа

По списку **candidates** (и/или одному path) определить **`Stack`**:

- primary language;
- frameworks / runtime hints;
- markers, которые сработали.

Без facade, без cache, без CLI, без git subprocess (флаг `is_git_repo` уже есть с M2.1).

---

## 2. Контекст

Из vision:

> detect — Языки и фреймворки → `Stack` / `Project`.  
> Откуда берётся стек? detect по markers/файлам, **не** по shebang alone.

Из M1.2 `Stack`:

```rust
pub struct Stack {
    pub language: Option<String>,
    pub frameworks: Vec<String>,
    pub markers: Vec<String>,
}
```

M2.2 заполняет эти поля детерминированно.

## 4. Правила детекта

### 4.1. Language из marker hints

Приоритет при нескольких language_hint в одном candidate:

1. Явные «сильные» манифесты: `Cargo.toml` → Rust, `go.mod` → Go, `pom.xml` → Java, …
2. Если конфликт (например `Cargo.toml` + `package.json`) — **все** markers в `Stack.markers`, language = **первый по таблице приоритетов** или `None` + frameworks из обоих.  
   **Рекомендация MVP:** приоритетный список; при равном приоритете — первый hit в отсортированном списке markers.

Пример приоритета (высокий → низкий):

```text
Cargo.toml > go.mod > pom.xml / build.gradle* > package.json > pyproject.toml > setup.py > requirements.txt > Gemfile > composer.json > CMakeLists.txt > Makefile
```

Зафиксировать таблицу в коде как `const` / static data + тест на порядок.

### 4.2. Frameworks

Дополнительные файлы/dirs **внутри** candidate path (один уровень или shallow), не полный recursive content scan:

| Наблюдение | Framework hint |
|------------|----------------|
| `package.json` + зависимость/поле `next` (optional read) | Next.js |
| файл `next.config.js` / `next.config.mjs` | Next.js |
| `Cargo.toml` + `[dependencies] axum` (optional) | Axum |
| dir `app/` + `package.json` (Next app router) | — осторожно, эвристика |
| `manage.py` + Django-ish | Django |
| `angular.json` | Angular |
| `vue.config.js` / `"vue"` | Vue |
| `deno.json` | Deno |
| `build.sbt` | Scala/sbt |

**MVP-ограничение:** framework detect **без** парсинга JSON/TOML содержимого допустим на уровне **имён файлов**:

- `next.config.*` → `frameworks: ["Next.js"]`
- `nuxt.config.*` → Nuxt
- `angular.json` → Angular
- `vite.config.*` → Vite
- `django` manage.py → Django
- `Gemfile` + `config/application.rb` → Rails (если есть)

Парсинг `package.json` / `Cargo.toml` для deps — **желательно**, но не блокер MVP; можно feature-flag или отложить на Alpha. В спецификации этапа:

- **Обязательно:** framework hints по **именам файлов**.
- **Опционально (если успеваете):** лёгкий parse `package.json` keys `dependencies`/`devDependencies` для next/react/vue.

Не тянуть тяжёлые parser-экосистемы без нужды.

### 4.3. Markers field

`Stack.markers` = список **имён** сработавших marker files/dirs (из `ProjectCandidate.markers`), отсортированный стабильно.

## 5. API

```rust
use crate::domain::Stack;
use crate::scan::ProjectCandidate;
use std::path::Path;

/// Build Stack from an already discovered candidate (markers known).
pub fn stack_from_candidate(candidate: &ProjectCandidate) -> Stack;

/// Optionally enrich frameworks by looking at shallow files under candidate.path.
pub fn detect_stack(path: &Path, markers: &[MarkerHit]) -> Result<Stack, Error>;

/// Batch helper.
pub fn detect_stacks(candidates: &[ProjectCandidate]) -> Vec<(ProjectCandidate, Stack)>;
```

Рекомендуемый поток M2.3:

```text
find_candidates → for each: stack_from_candidate (+ optional enrich) → Project { stack, … }
```

`detect_stack` нужен, когда markers ещё не собраны (редко) или для unit-тестов path-only.

### Ошибки

- path не dir → `NotADirectory`
- IO при shallow read → `Error::Io`  
Для batch: один failing path не обязан ронять все (решить: fail-fast vs partial). **MVP: fail-fast** в `detect_stacks` или возвращать `Result` per item — предпочтительно `Vec<Result<...>>` не усложнять; simple `Result<Vec<_>>` fail-fast.

## 6. Сборка `Project` (подготовка к M2.3)

Не обязательно полный `Project` в M2.2, но удобный helper:

```rust
pub fn candidate_to_project(
    candidate: ProjectCandidate,
    stack: Stack,
    size_bytes: u64, // 0 если ещё не считали
) -> Project {
    Project {
        path: candidate.path,
        name: candidate.name,
        stack,
        size_bytes,
        is_git_repo: candidate.is_git_repo,
    }
}
```

Подсчёт `size_bytes` — отдельная функция (может жить в scan):

```rust
/// Sum file sizes under project path, respecting SkipPolicy (no follow links).
pub fn project_size_bytes(path: &Path, policy: &SkipPolicy, max_depth: usize) -> Result<u64, Error>;
```

Можно сделать в M2.2 или M2.3. **Рекомендация:** реализовать в M2.2 как util, чтобы sniff сразу отдавал размеры.

Алгоритм size: walk с policy, суммировать `metadata.len()` для files; dirs skip по policy; ошибки metadata — skip file или Error (MVP: skip + continue безопаснее для UX).

## 7. Тесты (обязательные)

1. `Cargo.toml` only → language `Some("Rust")`, markers contains `Cargo.toml`.
2. `package.json` + `next.config.js` → language JS/TS, frameworks contains `Next.js`.
3. `go.mod` → Go.
4. Конфликт `Cargo.toml` + `package.json` → language по приоритету, оба marker в списке.
5. Только `.git` → language None, is_git_repo true (на candidate), markers содержит `.git`.
6. `stack_from_candidate` не ходит в FS (pure).
7. `detect_stack` / enrich видит framework file.
8. `project_size_bytes`: известная fixture с 2 файлами → ожидаемая сумма; `node_modules` не входит.
9. Детерминизм: одинаковый input → одинаковый `Stack` (порядок frameworks/markers стабилен).

Команда:

```bash
cargo test -p raccpack-core detect stack
```

## 8. Ограничения и запреты

- Не использовать shebang (`#!/usr/bin/env python`) как primary detect в MVP.
- Не сканировать весь content на секреты.
- Не вызывать `git` binary.
- Не менять schema `Stack` breaking-образом (поля уже в M1.2).
- Не добавлять UI-зависимости.
- Парсинг манифестов — только если лёгкий и тестируемый; иначе filename-only.
