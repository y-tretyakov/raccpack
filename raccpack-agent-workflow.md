# Workflow: главный агент, субагенты, приёмка, тесты, документация

## Цель документа

Описать **рабочий процесс**, в котором:

1. Есть **один главный агент** (Orchestrator).
2. Он **только** планирует, делегирует, принимает работу и проверяет итог.
3. **Не** пишет production-код сам (кроме минимальных правок плана/WORKLOG, если это явно нужно для координации).
4. Субагенты делают реализацию и тесты.
5. Разработка и тесты по одной фиче идут **параллельно**.
6. После всех фаз Orchestrator сам верифицирует, затем делегирует документацию.

Источник задач: `raccpack-agent-prompt.md` (фазы 0–11, этапы X.Y).

---

## Роли

### 1. Orchestrator (главный агент)

**Делает:**

- Читает промпт этапов и CODE_REVIEW / CHANGES.
- Строит и обновляет **план** (какие этапы в какой очереди, зависимости).
- На каждый активный этап назначает:
  - **Dev-субагента** — реализация;
  - **Test-субагента** — тесты на ту же функциональность (параллельно).
- Принимает или **отклоняет** результат субагента по чеклисту этапа.
- При отклонении возвращает задачу с **конкретным** списком замечаний (не «переделай нормально»).
- После закрытия всех этапов — **финальная проверка** (сборка, тесты, сверка с критериями).
- После успешной финальной проверки — делегирует **Docs-субагента**.

**Не делает:**

- Большие правки кода «за» dev-субагента.
- Смешивание 3+ этапов в одну делегацию.
- Приёмку «на глаз» без чеклиста критерия готовности из промпта.

### 2. Dev-субагент

**Делает:** только код/рефакторинг этапа X.Y по ТЗ от Orchestrator.

**На входе получает:**

- Номер этапа и дословный критерий готовности из промпта.
- Список файлов, которые можно трогать (и которые нельзя).
- Контекст: зависимости от предыдущих (уже закрытых) этапов.
- Запреты (anyhow в API, unwrap в prod, ломать PATTERNS без тестов и т.д.).

**На выходе отдаёт:**

- Отчёт формата «Этап X.Y» из промпта.
- Список изменённых файлов.
- Как запустить релевантные тесты (даже если тесты пишет другой субагент — dev указывает smoke-команды).

### 3. Test-субагент

**Делает:** тесты **для того же этапа X.Y**, параллельно с Dev.

**На входе получает:**

- То же ТЗ этапа (поведение, API, edge cases).
- Ожидаемые public/internal функции, которые появятся или изменятся.
- Что **не** тестировать (чужие модули).

**На выходе отдаёт:**

- Новые/обновлённые `#[test]` / integration tests.
- Описание: что покрыто, что flaky, что требует git/FS.
- Команда запуска узкого набора тестов.

**Важно:** Test-субагент пишет тесты по **спецификации этапа**, а не «после того как увидел код dev». Допустимо опираться на имена API из ТЗ. Если dev ещё не смержил код — тесты могут временно не компилироваться; Orchestrator стыкует после обеих сдач.

### 4. Docs-субагент

**Делает только после** финальной приёмки всех dev/test этапов:

- Обновление `CHANGES.md`, `MIGRATION.md`.
- Краткие module-level rustdoc, если этап 9.2 не закрыл всё.
- Не меняет поведение кода (кроме опечаток в комментариях).

## Жизненный цикл одной фазы

```
                    ┌─────────────────────────┐
                    │  Orchestrator: план     │
                    │  выбрать этап X.Y       │
                    └───────────┬─────────────┘
                                │
              ┌─────────────────┴─────────────────┐
              ▼                                   ▼
   ┌──────────────────┐                ┌──────────────────┐
   │ Dev-субагент     │                │ Test-субагент    │
   │ реализация X.Y   │                │ тесты для X.Y    │
   └────────┬─────────┘                └────────┬─────────┘
            │                                   │
            └─────────────────┬─────────────────┘
                              ▼
                 ┌────────────────────────┐
                 │ Orchestrator: приёмка  │
                 │ обоих артефактов       │
                 └────────────┬───────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
         оба OK          dev FAIL         test FAIL
              │               │               │
              │               └── rework dev  │
              │                   only        │
              │               ◄───────────────┘
              │               rework test only
              ▼
         этап X.Y CLOSED → следующий этап
```

### Параллельность

- На **один** этап X.Y всегда два поручения: Dev и Test **одновременно**.
- Не запускай Dev этапа X.Y+1, пока X.Y не CLOSED (кроме явно независимых веток — см. «Параллельные этапы» ниже).
- Test для X.Y **не** ждёт завершения Dev; стыковка на приёмке.

### Параллельные этапы (исключения)

Orchestrator **может** вести две линии, если промпт не связывает их данными:

| Линия A | Линия B | Можно параллельно? |
|---------|---------|-------------------|
| 1.x EnabledGroups | 2.x fingerprint/mask | да |
| 2.x | 3.x pack policy | да, если 3 не зависит от fingerprint |
| 4.x Git trait | 5.1 parallel_jobs | да |
| 7.x WalkSession | 8.x pattern order tests | да (8 только тесты таблиц) |
| 7.3 и 7.4 | нет | строго последовательно |

Правило: если оба этапа правят **один и тот же файл** — только последовательно.

## Делегирование: шаблон поручения Dev

Orchestrator отправляет субагенту текст вида:

```markdown
# Задача Dev: этап X.Y — <название>

## Контекст
- Репозиторий: raccpack-core (пишется с нуля; этапы 0–11 выполняются по порядку).
- Предыдущий закрытый этап: …
- Файлы, которые УЖЕ содержат нужный API: …

## ТЗ (дословно из промпта)
<вставить блок этапа из raccpack-agent-prompt.md>

## Ограничения
- Не трогать: <список путей>
- Нельзя: anyhow в public Error, unwrap в non-test, менять порядок PATTERNS без падающего теста.
- Стиль: как соседний код, rustfmt.

## Критерий приёмки
- [ ] <критерий из промпта>
- [ ] Отчёт в формате этапа
- [ ] Перечень файлов diff

## Как сдать
Верни отчёт + список команд для smoke-проверки.
```

## Делегирование: шаблон поручения Test

```markdown
# Задача Test: этап X.Y — тесты для <название>

## Поведение, которое нужно покрыть
<из ТЗ этапа: функции, edge cases, ошибки>

## Ожидаемый API (имя/сигнатуры из ТЗ)
- `...`

## Обязательные кейсы
1. …
2. …
3. негативный кейс: …

## Где класть тесты
- unit: рядом с модулем `#[cfg(test)]`
- integration: только если нужен FS/git; тогда tempfile, без сети

## Ограничения
- Не менять production-логику (только `#[cfg(test)]` и test support).
- Не зависеть от реального `git` без `#[ignore]` / feature.

## Критерий приёмки
- [ ] Кейсы из списка покрыты
- [ ] Тесты детерминированы
- [ ] Команда запуска узкого набора указана
```

## Приёмка работы субагента (строго)

Orchestrator **принимает** только если выполнены **все** пункты:

### Для Dev

1. Критерий готовности этапа из промпта — да.
2. Нет запрещённых паттернов (anyhow в API, новый `unwrap` в prod, silent default config и т.д.).
3. Затронуты только согласованные файлы (или отклонения объяснены).
4. Отчёт заполнен (Сделано / Файлы / Тесты / Риски).
5. Если этап менял public API — есть пометка breaking для CHANGES.

### Для Test

1. Есть тесты на каждый **обязательный кейс** из поручения.
2. Тесты не требуют ручного setup вне tempfile/cfg.
3. Имена тестов читаемые; нет `#[test] fn test1`.
4. Указана команда запуска.

### Если не принято

Orchestrator возвращает **Rework ticket**:

```markdown
# Rework: этап X.Y (Dev|Test), попытка N

## Что не принято
1. <конкретный факт>
2. …

## Что сделать
1. …
2. …

## Что уже хорошо (не ломать)
- …
```

Лимит попыток на этап: **3**. После 3 неудач — Orchestrator эскалирует человеку (короткий отчёт: этап, причины, варианты).

---

## Стыковка Dev + Test на одном этапе

1. Оба сдали артефакты.
2. Orchestrator (или короткий merge-шаг) убеждается, что тесты компилируются с кодом dev.
3. Запуск узкого набора тестов этапа.
4. Если тесты красные из-за бага в коде → rework **Dev**.
5. Если тесты неверны относительно ТЗ → rework **Test**.
6. Если ТЗ двусмысленно — Orchestrator уточняет ТЗ и перезапускает обоих.

**Нельзя** принять этап с красными тестами этапа, пометив «потом починим».

## Финальная проверка (делает Orchestrator сам)

После статуса `done` у всех обязательных этапов:

### Checklist FINAL

1. **Сборка:** `cargo test` (или эквивалент проекта) — green.
2. **Сверка этапов:** пройти таблицу этапов; каждый обязательный пункт либо `done`, либо `explicitly deferred` с причиной в WORKLOG.
3. **Запреты:**
   - нет `Error::Any` / anyhow в library Error;
   - нет `Box<dyn Error>` в public config API;
   - нет `WalkDir` без `follow_links(false)` в production paths;
   - SensitiveRisk upgrade только через severity API.
4. **Безопасность (минимум):** pack не молчит про content-secrets, если этап 3.2 done; masked не светит длинный prefix, если 2.2 done.
5. **Регрессия domain:** sensitive filename/content tests зелёные.
6. **WORKLOG** полный: каждый этап с датой/статусом.

Если любой пункт FINAL падает — **не** вызывать Docs. Открыть rework на конкретный этап.

## Делегирование документации (после FINAL OK)

```markdown
# Задача Docs

## Вход
- WORKLOG со всеми закрытыми этапами
- CHANGES.md (текущий)
- Diff/summary по фазам 1–11

## Сделать
1. Обновить CHANGES.md: секции по фазам, breaking changes.
2. MIGRATION.md: до/после для CLI (load, den_dir, Error match, RaidResult.success, …).
3. Краткий ARCHITECTURE.md (опционально): SkipPolicy, GitClient, WalkSession, severity API.
4. Не менять runtime-код.

## Критерий
- Новый человек по MIGRATION.md сможет перевести CLI за 15 минут.
- CHANGES совпадает с фактом в коде (Orchestrator выборочно сверит 3 пункта).
```

Orchestrator **принимает** документацию так же строго: выборочная сверка 3+ утверждений с кодом. Неверное утверждение → rework Docs.

## Коммуникация и артефакты

| Артефакт | Кто пишет | Когда |
|----------|-----------|--------|
| `WORKLOG.md` | Orchestrator | постоянно |
| Отчёт этапа | Dev / Test | при сдаче |
| Rework ticket | Orchestrator | при отказе |
| `CHANGES.md` / `MIGRATION.md` | Docs (финал) + правки Orchestrator | после FINAL |
| План backlog | Orchestrator | старт + обновления |

Имена субагентов в логе: `dev-1.2`, `test-1.2`, `docs-final` — чтобы было видно параллельность.

---

## Анти-паттерны (запрещено)

1. Orchestrator сам реализует этап «чтобы быстрее».
2. Приёмка Dev без параллельного (или догнавшего) Test для того же этапа — **исключение:** этапы 0.1, 7.1 (design-only) могут быть без Test-субагента; тогда Orchestrator явно пишет `test: n/a (design)`.
3. Делегация «сделай фазы 1–3 целиком».
4. Test-субагент меняет production-код «заодно».
5. Docs до зелёного FINAL.
6. Закрытие этапа с обещанием «тесты потом».
7. Игнор rework после 1-й неудачи без нового ticket.

---

## Минимальный сценарий «день 1»

1. Orchestrator: этап 0.1 → dev (inventory only, test n/a).
2. Приёмка 0.1 → 0.2 baseline.
3. Параллельно: **dev-1.1** + **test-1.1**.
4. Приёмка 1.1 → параллельно 1.2 dev+test.
5. Не начинать 7.x, пока 1.x и 2.x не стабильны (меньше merge-конфликтов в sensitive).

---

## Критерий успеха всего workflow

- Все обязательные этапы промпта в статусе `done`.
- FINAL checklist пройден Orchestrator’ом.
- Документация принята.
- В WORKLOG нет скрытых `deferred` без причины.

На этом работа главного агента по проекту считается завершённой.
